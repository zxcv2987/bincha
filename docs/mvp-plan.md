# Bincha MVP 계획

> 이 문서는 1차로 실제 사용자에게 검증할 **최소 범위**를 정의한다.
> 전체 비전과 최종 로드맵은 [[product-plan|제품 기획서(최종 Plan)]]을 참고한다.
> 성과(Achievement) / 측정(Measurement) / 근거 타입(Evidence)은 이 문서 범위에 포함하지 않는다. 결과 기록이 실사용으로 몇 주 쌓여 "여러 결과를 하나로 묶고 싶다"는 신호가 확인된 뒤 설계한다.

---

## 1. 검증하려는 가설

> 할 일을 완료한 뒤, 실제로 무엇을 했는지 짧게 기록하는 습관이 생기는가?

이 한 가지만 먼저 검증한다. 성과 정리·측정·회고는 이 가설이 맞다고 확인된 뒤에 의미가 있다.

---

## 2. MVP 범위

### 포함

**P0 — 선행 조건 (스코프 축소와 무관하게 즉시 처리)**
- 사용자별 데이터 분리 (`user_id` 기반 Category/Todo 소유권)

**P1 — 할 일**
- 카테고리 생성 / 이름 수정 / 삭제 / 순서 변경
- 할 일 생성 / 수정 / 삭제
- 할 일 완료 / 완료 취소
- 완료일 기록
- 진행 중 · 완료 필터

**P2 — 실행 결과**
- 결과 생성 / 수정 / 삭제
- 완료된 할 일과 1:1 연결
- 결과 기록 대기 목록
- 관련 URL 1개 (텍스트 필드, 별도 Evidence 모델 아님)
- 측정 필요 여부 체크(값만 저장, 측정 기능 자체는 미구현)

### 제외 (최종 방향 로드맵 P3 이후로 이연)

- Achievement 모델 및 화면
- Measurement 모델 및 화면
- Evidence 별도 모델/타입(enum)
- 회고 화면
- AI 보조
- 외부 서비스 연동(GitHub/Notion/Slack)

## 3. 데이터 모델

기술 제안서의 목표 스키마 중 P0~P2에 필요한 부분만 사용한다.

```text
user
├─ category (user_id 추가)
└─ todos (user_id 추가)
    └─ task_result (0..1)
```

```prisma
model task_result {
  id                BigInt   @id @default(autoincrement())
  created_at        DateTime @default(now()) @db.Timestamptz(6)
  updated_at        DateTime @updatedAt @db.Timestamptz(6)

  todo_id           BigInt   @unique
  user_id           BigInt

  summary           String
  change_summary    String   @default("")
  unexpected        String   @default("")
  next_action       String   @default("")
  evidence_url      String   @default("")
  needs_measurement Boolean  @default(false)

  todo              todos    @relation(fields: [todo_id], references: [id], onDelete: Cascade)
  user              user     @relation(fields: [user_id], references: [id])

  @@index([user_id])
}
```

Evidence는 별도 모델·enum 없이 `evidence_url` 텍스트 필드 하나로 시작한다. PR/이슈/문서 타입 구분은 지금 어떤 필터링·통계에도 쓰이지 않으므로 만들지 않는다.

## 4. 핵심 사용자 흐름

### 4.1 할 일 등록
```text
할 일 추가 버튼 선택 → 제목 입력 → 카테고리 선택 → (선택) 설명 입력 → 저장
```

### 4.1.1 카테고리 관리
```text
사이드바의 관리 선택 → 카테고리 이름 수정 또는 순서 변경 → 즉시 저장
```

카테고리 순서는 사용자별로 저장한다. 이름 수정과 순서 변경은 각각 완료되는 즉시 반영하며, 별도의 전체 저장 단계는 두지 않는다.

### 4.2 할 일 완료
```text
체크박스 선택 → 완료 상태 저장 → 완료 안내 표시 → 결과 기록 또는 나중에 기록 선택
```

### 4.3 결과 기록
```text
완료 직후 결과 기록 선택 → 실제 수행 내용 입력 → 변화한 점 입력 → 관련 링크 추가 → 측정 필요 여부 선택 → 저장
```

### 4.4 나중에 결과 기록
```text
결과를 입력하지 않고 완료 → 결과함의 기록 대기 목록에 저장 → 사용자가 나중에 결과 입력
```

## 5. 화면

### 5.1 할 일 목록

```text
[ ] 로그인 E2E 테스트 작성
    로그인 주요 시나리오를 자동화한다.
    개발
```

완료 후:
```text
[x] 로그인 E2E 테스트 작성
    완료: 2026-07-27
    결과 기록 대기
    [결과 기록]
```

결과 기록 후:
```text
[x] 로그인 E2E 테스트 작성
    결과 기록됨
    [결과 보기]
```

### 5.2 결과 기록 화면

```text
실제로 무엇을 했나요?             필수
무엇이 달라졌나요?                 선택
예상과 달랐던 점이 있나요?         선택
다음에 이어서 할 일이 있나요?       선택
관련 링크                           선택
[ ] 나중에 측정 필요
```

### 5.3 결과함

```text
결과 기록 대기
- 로그인 E2E 테스트 작성 (완료일: 2026-07-27) [결과 기록]

결과 기록 완료
- 로그인 시나리오 5개를 자동화했다.
  연결된 할 일: 로그인 E2E 테스트 작성
```

## 6. 주요 정책

- 결과를 작성하지 않고도 할 일을 완료할 수 있다(완료를 막지 않는다).
- 완료 취소를 해도 기존 결과는 유지되며, 다시 완료하면 이어서 수정할 수 있다.
- 결과가 없는 할 일은 바로 삭제 가능. 결과가 있으면 삭제 전 경고.
- 카테고리 삭제 시 안의 할 일은 다른 카테고리로 이동하거나 삭제를 취소해야 한다(카테고리 cascade 삭제 금지).
- 카테고리 이름은 사용자 안에서 중복될 수 없다.
- 카테고리 순서 변경은 다른 사용자의 카테고리에 영향을 주지 않는다.

---

## 7. MVP 완료 조건

- 사용자는 자신의 데이터만 조회·수정·삭제할 수 있다.
- 새로고침 후 완료 상태가 유지된다.
- 완료 취소가 가능하다.
- 완료된 할 일에만 결과를 기록할 수 있고, 할 일 하나에 결과는 하나만 생성된다.
- 결과 기록 대기 목록을 확인할 수 있다.

---

## 8. 검증 시나리오

### 시나리오 1: 일반 완료
```text
할 일: 버튼 간격 수정
처리: 빠른 완료
결과: 기록하지 않음
```

### 시나리오 2: 결과 기록
```text
할 일: 로그인 E2E 테스트 작성
결과: 로그인 주요 시나리오 5개를 자동화했다.
근거: GitHub Pull Request URL
```

---

## 9. 초기 성공 지표

- 주간 할 일 완료 수
- 완료 작업 중 결과 기록 비율 (목표: 30% 이상)
- 결과 작성 평균 소요 시간 (목표: 1분 이하)
- 결과 기록 대기 건수
- 4주 연속 사용 여부

---

## 10. 다음 단계로 넘어가는 기준

결과 기록이 몇 주 쌓이고 "여러 결과를 하나의 성과로 묶고 싶다"는 신호가 실제로 확인되면 그때 Achievement 설계를 시작한다. 지금 스키마를 미리 굳히지 않는다 — 실사용 패턴과 다르게 굳어질 위험이 더 크다. 상세는 [[product-plan]] 13장, 17장 참고.
