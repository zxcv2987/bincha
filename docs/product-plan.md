# Bincha 제품 기획서

##  1. 문서 목적

이 문서는 기존 할 일 관리 서비스인 Bincha를 다음 흐름을 지원하는 개인 작업 관리 도구로 확장하기 위한 제품 방향과 MVP 범위를 정의한다.

```text
할 일 기록
→ 실행
→ 완료
→ 결과 기록
→ 성과 후보 생성
→ 측정
→ 성과 확정
```

Bincha는 단순히 해야 할 일을 관리하는 도구가 아니라, 사용자가 완료한 작업을 실행 결과와 성과로 축적할 수 있도록 돕는 것을 목표로 한다.

> 이 문서는 Bincha의 **최종 방향(전체 로드맵)**을 정의한다.
> 실제로 1차 출시할 범위는 [[mvp-plan|MVP 계획]] 문서를 따른다.
> Achievement / Measurement / Evidence는 최종 방향에 포함되지만 MVP 범위는 아니다 — 결과 기록이 실사용으로 몇 주 쌓인 뒤 설계를 확정한다.

---

## 2. 제품 개요

### 2.1 제품명

**Bincha**

### 2.2 제품 정의

> Bincha는 할 일을 끝내는 데서 멈추지 않고, 실행 결과와 근거를 기록하여 장기적으로 활용 가능한 성과로 전환하는 개인 작업 관리 도구다.

### 2.3 핵심 메시지

> 완료한 일은 사라지지 않고 성과가 된다.

### 2.4 짧은 소개

> 오늘 한 일을 내일 활용할 수 있는 기록으로 만드세요.

## 3. 배경

기존 Bincha는 다음 기능을 제공하는 개인 Todo List로 시작했다.

- 할 일 생성
- 할 일 수정
- 할 일 삭제
- 카테고리 생성 및 삭제
- 카테고리별 필터링
- 로그인 및 로그아웃
- 읽기 전용 화면

현재 구조에서는 사용자가 할 일을 완료하더라도 다음 정보가 남지 않는다.

- 실제로 무엇을 수행했는지
- 수행 결과 무엇이 달라졌는지
- 왜 특정 방법을 선택했는지
- 작업을 증명할 수 있는 자료가 무엇인지
- 여러 작업이 어떤 하나의 성과로 이어졌는지
- 성과를 수치로 확인할 수 있는지

그 결과 사용자는 시간이 지난 뒤 자신이 했던 일을 정확히 기억하기 어렵다.

예를 들어 다음과 같은 작업 제목만 남을 수 있다.

```text
로그인 테스트 작성
관리자 화면 개선
운영 문서 작성
검색 필터 수정
```

하지만 이력서, 포트폴리오, 면접, 업무 회고에 필요한 것은 단순한 작업 제목이 아니다.

```text
핵심 로그인 시나리오를 자동화하여
배포 전 회귀 오류를 발견할 수 있는 검증 기반을 구축했다.
```

Bincha는 할 일과 성과 사이의 기록 공백을 해결한다.

## 4. 문제 정의

### 4.1 완료된 작업이 사라진다

일반적인 Todo 서비스에서 완료된 작업은 체크된 항목이나 과거 목록으로 남을 뿐이다.

사용자가 그 작업으로 무엇을 만들었고 어떤 변화가 있었는지는 기록되지 않는다.

### 4.2 결과 기록이 여러 곳에 흩어진다

작업과 관련된 정보는 다음 위치에 분산될 수 있다.

- GitHub Pull Request
- GitHub Issue
- Notion 문서
- 업무 메신저
- 개인 메모
- 배포 링크
- 기억

분산된 기록은 시간이 지날수록 다시 찾거나 하나의 성과로 정리하기 어려워진다.

### 4.3 성과를 나중에 측정하기 어렵다

작업 직후에는 성과 수치가 없는 경우가 많다.

예를 들어 테스트를 추가한 직후에는 다음 수치를 바로 알 수 없다.

- 회귀 오류가 얼마나 줄었는지
- 수동 QA 시간이 얼마나 감소했는지
- 배포 전에 오류를 몇 건 발견했는지

측정 계획을 남기지 않으면 나중에 성과를 확인할 기회도 사라진다.

### 4.4 여러 작업이 하나의 성과로 연결되지 않는다

실제 성과는 하나의 작업만으로 만들어지지 않는 경우가 많다.

예를 들어 다음 작업들은 각각 독립된 Todo다.

```text
로그인 E2E 테스트 작성
GitHub Actions 실행 구성
테스트 실패 알림 추가
배포 절차 문서화
```

하지만 이 작업들은 다음과 같은 하나의 성과로 묶일 수 있다.

```text
핵심 로그인 흐름에 대한 자동 검증 환경을 구축하여
배포 전 회귀 오류를 발견할 수 있는 기반을 마련했다.
```

## 5. 제품 목표

### 5.1 작업 기록의 부담을 낮춘다

사용자는 기존 Todo 앱처럼 빠르게 할 일을 등록할 수 있어야 한다.

할 일을 만들 때부터 성과나 결과를 자세히 작성하도록 요구하지 않는다.

### 5.2 완료 이후 결과를 남길 수 있게 한다

사용자는 할 일을 완료한 뒤 실제 수행 내용과 변화한 점을 기록할 수 있어야 한다.

### 5.3 여러 결과를 하나의 성과로 묶는다

하나 이상의 작업 결과를 선택하여 하나의 성과로 정리할 수 있어야 한다.

### 5.4 아직 확인되지 않은 성과를 측정한다

수치가 없는 결과는 과장된 성과로 확정하지 않고 측정 대기 상태로 관리한다.

### 5.5 축적된 성과를 다시 활용한다

확정된 성과는 다음 용도로 활용할 수 있어야 한다.

- 이력서
- 포트폴리오
- 면접 답변
- 주간 업무 보고
- 월간 회고
- 연말 회고

## 6. 비목표

Bincha는 MVP 단계에서 종합 프로젝트 관리 도구를 목표로 하지 않는다.

다음 기능은 초기 범위에서 제외한다.

- 팀 협업
- 조직 권한 관리
- 실시간 공동 편집
- 복잡한 프로젝트 일정 관리
- 칸반 보드
- 간트 차트
- 하위 작업
- 반복 일정
- 업무 시간 측정
- Slack 및 Notion 양방향 동기화
- GitHub Pull Request 자동 수집
- AI의 완전 자동 성과 확정

## 7. 핵심 사용자

### 7.1 주요 사용자

자신이 수행한 작업과 성장 과정을 기록하고 싶은 개인 사용자다.

초기에는 다음 사용자에게 집중한다.

- 개발자
- 취업 준비생
- 이직 준비자
- 개인 프로젝트를 진행하는 사람
- 업무 회고를 꾸준히 남기고 싶은 사람

### 7.2 초기 사용자 상황

사용자는 다음과 같은 요구를 가진다.

- 오늘 해야 할 일을 정리하고 싶다.
- 완료한 일을 간단히 기록하고 싶다.
- 나중에 이력서에 쓸 내용을 잊고 싶지 않다.
- 성과가 될 만한 작업만 별도로 모으고 싶다.
- 아직 수치가 없는 작업은 나중에 다시 확인하고 싶다.

## 8. 제품 원칙

### 8.1 할 일 등록은 가벼워야 한다

할 일 등록 시 필수 정보는 최소화한다.

```text
제목
카테고리
```

설명은 선택적으로 작성할 수 있다.

### 8.2 완료를 방해하지 않는다

할 일을 완료할 때마다 결과 입력을 강제하지 않는다.

완료는 즉시 처리하고 다음 선택지를 제공한다.

```text
할 일을 완료했습니다.

[결과 기록하기] [나중에]
```

### 8.3 모든 완료 작업을 성과로 만들지 않는다

다음 작업은 일반 완료 기록으로만 남을 수 있다.

- 오탈자 수정
- 단순 전달 업무
- 작은 스타일 변경
- 반복적인 유지보수
- 개인적인 간단한 심부름

### 8.4 결과와 성과를 구분한다

결과는 사용자가 실제로 수행한 내용이다.

성과는 그 결과가 만들어낸 가치다.

```text
결과:
로그인 테스트 5개를 작성했다.

성과:
핵심 로그인 흐름을 자동으로 검증하여
배포 전 회귀 오류를 발견할 수 있는 기반을 마련했다.
```

### 8.5 성과를 과장하지 않는다

성과 상태를 다음과 같이 구분한다.

```text
초안
→ 측정 중
→ 확인됨
```

실제 변화가 확인되지 않았다면 성과를 확정하지 않는다.

### 8.6 사용자가 최종 판단한다

AI가 도입되더라도 결과나 성과를 자동으로 확정하지 않는다.

```text
AI 제안
→ 사용자 확인
→ 사용자 수정
→ 저장
```

## 9. 핵심 개념

## 9.1 할 일

사용자가 앞으로 수행하려는 작업이다.

예시:

```text
로그인 E2E 테스트 작성
```

포함 정보:

- 제목
- 설명
- 카테고리
- 완료 여부
- 생성일
- 완료일

---

## 9.2 실행 결과

할 일을 수행한 뒤 실제로 무엇을 했는지 기록한 내용이다.

예시:

```text
이메일 로그인, 잘못된 비밀번호,
로그인 이후 리다이렉트 시나리오를 자동화했다.
```

포함 정보:

- 결과 요약
- 변화한 점
- 예상과 달랐던 점
- 후속 작업
- 관련 링크
- 측정 필요 여부

---

## 9.3 성과

하나 이상의 실행 결과가 만들어낸 가치다.

예시:

```text
핵심 로그인 시나리오와 배포 파이프라인을 연결하여
회귀 오류를 배포 전에 확인할 수 있는 검증 기반을 구축했다.
```

포함 정보:

- 성과 제목
- 해결하려던 문제
- 수행한 행동
- 선택한 방법과 이유
- 실제 결과
- 상태
- 연결된 실행 결과
- 측정 항목
- 관련 근거

---

## 9.4 측정

성과가 실제로 발생했는지 확인하기 위한 기록이다.

예시:

```text
측정 항목:
테스트 실패로 배포 전에 발견한 오류 수

기준값:
0건

실제값:
한 달 동안 3건

확인일:
2026-09-01
```

---

## 9.5 근거

작업과 성과를 뒷받침하는 자료다.

지원 대상:

- GitHub Pull Request
- GitHub Issue
- 문서 URL
- 배포 URL
- 이미지
- 테스트 결과
- 수치 기록
- 자유 메모

MVP에서는 URL과 텍스트 메모를 우선 지원한다.

## 10. 핵심 사용자 흐름

## 10.1 할 일 등록

```text
할 일 추가 버튼 선택
→ 제목 입력
→ 카테고리 선택
→ 필요하면 설명 입력

```

---

## 10.2 할 일 완료

```text
체크박스 선택
→ 완료 상태 저장
→ 완료 안내 표시
→ 결과 기록 또는 나중에 기록 선택
```

---

## 10.3 결과 기록

```text
완료 직후 결과 기록 선택
→ 실제 수행 내용 입력
→ 변화한 점 입력
→ 관련 링크 추가
→ 측정 필요 여부 선택
→ 저장
```

---

## 10.4 나중에 결과 기록

```text
결과를 입력하지 않고 완료
→ 결과함의 기록 대기 목록에 저장
→ 사용자가 나중에 결과 입력
```

---

## 10.5 성과 생성

```text
결과함 진입
→ 하나 이상의 결과 선택
→ 성과로 묶기 선택
→ 문제, 행동, 결과, 가치 작성
→ 성과 초안 저장
```

---

## 10.6 성과 측정

```text
성과 초안 생성
→ 측정 항목 작성
→ 확인 예정일 설정
→ 실제 수치 입력
→ 성과 확인 또는 보류
```

## 11. 정보 구조

초기 메뉴는 다음과 같이 구성한다.

```text
Bincha
├─ 할 일
├─ 결과함
├─ 성과
└─ 회고
```

### 11.1 할 일

기존 Bincha의 기본 화면이다.

포함 기능:

- 진행 중 할 일
- 완료한 할 일
- 카테고리 필터
- 할 일 생성
- 할 일 수정
- 할 일 삭제
- 완료 및 완료 취소
- 결과 기록 상태 표시

### 11.2 결과함

완료 이후 정리가 필요한 작업을 모은다.

상태:

- 결과 기록 대기
- 결과 기록 완료
- 성과 후보
- 성과에 포함됨

### 11.3 성과

성과 초안과 확정된 성과를 관리한다.

상태:

- 초안
- 측정 중
- 확인됨
- 보류

### 11.4 회고

특정 기간 동안 수행한 내용을 정리한다.

포함 내용:

- 완료한 작업
- 작성한 결과
- 생성한 성과
- 확인한 성과
- 측정이 필요한 항목
- 결과가 없는 완료 작업

## 12. 주요 화면 (최종 그림)

> 12.1~12.3 (할 일, 결과 기록, 결과함)은 MVP 범위. 12.4~12.5 (성과)는 MVP 이후. 상세는 [[mvp-plan|MVP 계획]] 참고.

## 12.1 할 일 목록

기존 카테고리별 목록 구조를 유지한다.

Todo 카드 예시:

```text
[ ] 로그인 E2E 테스트 작성

    로그인 주요 시나리오를 자동화한다.

    개발
```

완료 후:

```text
[x] 로그인 E2E 테스트 작성

    완료: 2026-07-27
    결과 기록 대기

    [결과 기록]
```

결과 기록 후:

```text
[x] 로그인 E2E 테스트 작성

    결과 기록됨
    성과 후보

    [결과 보기]
```

---

## 12.2 결과 기록 화면

필드:

```text
실제로 무엇을 했나요?             필수
무엇이 달라졌나요?                 선택
예상과 달랐던 점이 있나요?         선택
다음에 이어서 할 일이 있나요?       선택
관련 링크                           선택
```

추가 선택:

```text
[ ] 성과 후보로 표시
[ ] 나중에 측정 필요
```

## 12.3 결과함

### 결과 기록 대기


## 14. 주요 정책

## 14.1 빠른 완료

결과를 작성하지 않고도 할 일을 완료할 수 있다.

결과가 없는 완료 작업은 결과함의 기록 대기 상태로 표시한다.

## 14.2 완료 취소

결과가 연결된 작업도 완료 취소할 수 있다.

완료를 취소해도 기존 결과는 유지한다.

다시 완료하면 기존 결과를 이어서 수정할 수 있다.

## 14.3 할 일 삭제

결과가 없는 할 일은 바로 삭제할 수 있다.

결과가 있는 경우 삭제 전에 경고한다.

```text
이 작업에는 실행 결과가 연결되어 있습니다.
할 일과 결과를 함께 삭제할까요?
```

결과가 성과에 연결되어 있으면 기본적으로 삭제를 제한한다.

## 14.4 카테고리 삭제

카테고리 안에 할 일이 있으면 바로 삭제하지 않는다.

다음 중 하나를 선택하게 한다.

- 다른 카테고리로 이동
- 미분류 카테고리로 이동
- 삭제 취소

## 14.5 성과 삭제

성과를 삭제해도 연결된 할 일과 실행 결과는 유지한다.

## 14.6 성과 확정

성과는 사용자가 직접 확인 상태로 변경한다.

측정값이 없더라도 사용자가 정성적 근거를 입력하면 확인 상태로 변경할 수 있다.

### 15.1 핵심 지표

## 18. 향후 검토 사항

### 프로젝트 모델 도입

MVP에서는 기존 Category 구조를 유지한다.

사용 과정에서 다음 요구가 확인되면 별도 Project 모델을 도입한다.

- 프로젝트마다 여러 카테고리가 필요한 경우
- 프로젝트 단위 성과 통계가 필요한 경우
- 프로젝트별 기간과 목표가 필요한 경우
- 개인 업무와 회사 업무를 구분해야 하는 경우

### 개인 기록과 업무 기록 구분

초기에는 카테고리로 구분한다.

필요성이 확인되면 다음 구분을 추가한다.

- 업무
- 개인 프로젝트
- 학습
- 생활

### AI 도입 시점

사용자가 직접 결과와 성과를 기록하는 흐름이 검증된 이후 도입한다.

AI 기능보다 먼저 실제 기록 데이터가 축적되는 것이 중요하다.

## 19. 최종 방향

Bincha의 핵심 차별점은 더 많은 할 일을 관리하는 것이 아니다.

완료한 작업이 사라지지 않고 다음 단계로 발전하도록 만드는 것이다.

```text
할 일
→ 실행 결과
→ 근거
→ 성과
→ 회고와 활용
```

Bincha는 사용자가 자신이 한 일을 단순한 완료 목록이 아니라, 다시 꺼내 쓸 수 있는 개인 자산으로 축적하도록 돕는다.
